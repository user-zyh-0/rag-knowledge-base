# RAG 知识库问答系统

基于 **FastAPI + MySQL** 的最小可用 RAG（检索增强生成）实现。上传文档后自动切分、向量化入库；提问时检索最相关的片段交给大模型生成答案，并强制模型只依据检索到的资料作答。

> 已完成文档管理（上传 / 列表 / 删除）、问答接口（完整答案 / 流式逐字输出）、混合检索（BM25 + 向量 + RRF 融合）、Query 改写（多路检索）与多轮对话（`session_id` + 指代消解）。

## 功能

- **文档管理**：上传（自动切分 + 向量化）、列表、删除
- **结构化切分**：按 Markdown 标题切分（合并"只有标题无正文"的空壳块），无标题时自动退回固定长度切分
- **混合检索**：向量语义检索 + BM25 关键词检索双路召回，RRF 融合排序（见「设计说明」）
- **Query 改写**：把口语化问题改写成关键词组合后多路检索，解决"切片切多大"这类问法与资料术语不匹配的问题
- **多轮对话**：`session_id` 区分会话，历史**先用于消解指代再检索**，让"它跟 overlap 什么关系"能正确命中（见「设计说明」）
- **语义检索**：余弦相似度全表扫描，返回最相关的 Top-K 片段
- **防幻觉问答**：Prompt 约束模型只使用检索结果，资料不足时明确回答"资料中没有提到"
- **流式输出**：`/chat/stream` 逐字返回，首字延迟约 1 秒（见「设计说明」）
- **数据一致性**：删除文档时通过数据库外键级联，自动清除其全部向量块

## 技术栈

| 层 | 选型 |
|---|---|
| Web 框架 | FastAPI 0.142 + Pydantic 2 |
| ORM / 数据库 | SQLAlchemy 2.1 + MySQL 8（utf8mb4） |
| Embedding | 硅基流动 `BAAI/bge-m3`（1024 维，免费） |
| 中文分词 | jieba `lcut_for_search`（搜索引擎模式，长词再切子词以提高召回） |
| LLM | DeepSeek `deepseek-flash` |

## 快速开始

### 1. 准备环境

- Python 3.10+（开发环境为 3.13）
- MySQL 8.0（需提前创建数据库）

```sql
CREATE DATABASE rag_db DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### 2. 安装依赖

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

### 3. 配置环境变量

复制 `.env.example` 为 `.env`，填入自己的 Key：

```ini
MYSQL_URL=mysql+pymysql://root:你的密码@localhost:3306/rag_db?charset=utf8mb4

DEEPSEEK_API_KEY=sk-xxx
SILICONFLOW_API_KEY=sk-xxx
DEEPSEEK_BASE_URL=https://api.deepseek.com
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1

LLM_MODEL=deepseek-flash
EMBEDDING_MODEL=BAAI/bge-m3
```

- DeepSeek Key：https://platform.deepseek.com/api_keys
- 硅基流动 Key：https://cloud.siliconflow.cn/account/ak

> `MYSQL_URL` 中的 `+pymysql` 与 `?charset=utf8mb4` 都不能省略。密码含 `@ : / # %` 时需 URL 编码（如 `@` → `%40`）。

### 4. 启动

```bash
python main.py
```

打开 http://127.0.0.1:8000/docs ，在自动生成的 Swagger 页面里直接调用接口。

## 接口

| 方法 | 路径 | 说明 | 状态码 |
|---|---|---|---|
| `POST` | `/documents` | 上传文档（JSON：`filename` + `content`） | 201 / 409 重名 / 422 参数非法 |
| `GET` | `/documents` | 列出全部文档 | 200 |
| `DELETE` | `/documents/{doc_id}` | 删除文档及其全部向量块 | 200 / 404 不存在 / 422 非整数 |
| `POST` | `/chat` | 问答（带 `session_id` 则续接会话），返回 `session_id` + 答案 + 改写后的问题 | 200 / 422 参数非法 |
| `POST` | `/chat/stream` | 流式问答，`session_id` 通过响应头 `X-Session-Id` 返回 | 200 / 422 参数非法 |
| `GET` | `/sessions/{session_id}/messages` | 查询某个会话的历史消息 | 200 |

调用示例：

```bash
curl -X POST http://127.0.0.1:8000/documents \
  -H "Content-Type: application/json" \
  -d '{"filename": "计算机网络.txt", "content": "第一章：计算机网络体系结构……"}'
```

流式问答（加 `-N` 关闭 curl 缓冲才能看到逐字效果）：

```bash
curl -N -X POST http://127.0.0.1:8000/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"question": "切块长度和重叠分别设为多少？"}'
```

## 数据模型

```
documents (1) ──< chunks (N)

messages（独立表，按 session_id 索引）
```

- `documents`：文档元信息（文件名、字节数、块数、创建时间），`filename` 唯一
- `chunks`：文本块 + 1024 维向量（`BLOB` 存 JSON 序列化后的浮点数组）
- 外键 `chunks.doc_id → documents.id`，带 `ON DELETE CASCADE`
- `messages`：对话历史（`session_id` / `role` / `content` / `created_at`），`session_id` 建索引。
  **不与 `documents` 建外键**——一个会话可能问多个文档，是多对多关系，需要时另建关联表

删除采用 `cascade="all, delete-orphan"` + `passive_deletes=True` + 数据库外键级联三者配合：ORM 不加载子对象，只发一条 `DELETE`，由数据库完成级联。相比默认行为（先 `SELECT` 所有子行再逐条 `DELETE`），文档块数越多差距越大。

## 设计说明

**为什么暂时不用向量数据库**

当前 10 块规模下，纯 Python 余弦全表扫描单次约 0.9 ms；按线性外推，1 万块约 0.7 s、10 万块约 7 s。万级以下引入 ANN 索引收益为负，且实测 10 块时 numpy 向量化反而更慢（数组创建开销大于计算收益）。计划在块数超过 10 万时再引入索引层，届时只需替换 `retrieve()` 内部实现，对外接口不变。

**为什么向量直接存 MySQL**

`bge-m3` 输出已归一化（模长实测 1.000000），余弦相似度等价于点积，无需额外索引结构。每块向量约 22 KB，`BLOB` 上限 64 KB，当前占用约 35%。若改用更高维的 Embedding 模型（如 3072 维），需同步升级为 `MEDIUMBLOB`。

**切分策略对比：收益在上下文成本，不在召回率**

三组方案实测（同一份 `test1.txt`，4390 字符）：

| 方案 | 块数 | 平均块长 | 总字符 | 说明 |
|---|---|---|---|---|
| 固定长度 | 10 | 493 | **4930** | 每 500 字符一刀，重叠 60 |
| 按标题 | 36 | 120 | 4327 | 按 Markdown 标题切 |
| **按标题 + 合并空壳** | **29** | **149** | 4334 | 当前采用 |

两个数字值得注意：

- **固定切分那 4930 字符里有 540 是重复的**（9 次重叠 × 60），按标题切是**零重复**——不会出现"同一段话在相邻两块里各存一份、检索时被重复命中、白花 prompt token"。
- **按标题切会产生「空壳块」**：`## 1 Web 后端开发笔记` 这类一级标题下面只有分隔线、正文全在子标题里，8 个一级标题块中 7 个是空壳（70~89 字符）。**不能简单按长度过滤**——长度 < 80 的块共 14 个，其中 7 个空壳该合并、7 个是有实际内容的短块（如 `7.3 作息调整` 58 字符）该保留。判断标准是"去掉标题行和分隔线后还有没有正文"。

检索效果对比（6 个问题，`k` 取 3）：

| 配置 | 命中率 | top-3 总字符 | 平均每问 |
|---|---|---|---|
| 固定长度（10 块） | 6/6 | 8200 | 1366 |
| 按标题（29 块） | 6/6 | **3810** | **635** |

**命中率完全相同，但上下文成本省了 53%。**

> 结论：**切分优化的衡量指标是「上下文成本」和「信息密度」，不是召回率。** 召回率主要由检索算法决定；切分影响的是"你为同样的答案付多少 token"——块更细更聚焦，同样召回 3 块不会夹带无关主题的内容。

**通用性处理**：按 `#` 切依赖文档有结构标记，纯文本会退化成一块。所以采用分层策略——检测到 `^#{1,6} ` 走标题切分，否则退回固定长度切分。真实项目里文档格式通常是已知的（上传时就知道是 md / pdf / docx），按格式选解析器比写万能正则靠谱。

**混合检索：为什么用 RRF 而不是加权求和**

向量检索管"意思像不像"，BM25 管"字面中没中"，两者的盲区正好互补。实测（10 块语料）：

| 提问 | 向量 Top3 | BM25 Top3 | 融合 Top3 |
|---|---|---|---|
| `top_k 取多少` | 9, 4, 6 | 9, 4, 6 | 9, 4, 6 |
| `400` | 1, 9, **8**（无关） | 9, 0, 3 | **9, 1, 0**（3/3 都真含 400） |
| `怎么防止模型乱编` | **2**, 5, 3 | 3, **4**, 9 | 3, 4, 9 |

第 2 行是融合价值的直接证据：向量单路精确率 2/3，BM25 单路虽 3/3 却把含 HTTP 400 的块排到第 4 而漏出 Top3，融合后两路漏掉的互相补上。

**不能用加权求和**：BM25 分数是无上限长尾（实测 7.919 / 4.028 / 1.850），余弦被压在 0~1 且高度聚集（0.476 / 0.439 / 0.415，相邻只差 0.03）。两者尺度差一个数量级，直接相加等于让 BM25 单方面决定结果。

**RRF（Reciprocal Rank Fusion）只看名次，不看分数**：

```
score(d) = Σ 1 / (60 + rank_i(d))
```

两个参数必须分开命名，否则极易混淆：`pool` 是每路召回的候选数，`rrf_k` 是平滑常数 60。

已知局限（均为实测）：

- **分数被压缩**：`pool` 等于语料总量时，每个块都被两路命中，分数全挤在 0.031~0.033（相对差仅 5%）。此时 RRF 退化成"两路名次平均"——`pool` 的真正作用是制造「单路命中 vs 双路命中」的 2 倍差异，所以 `pool` 应远小于语料规模。
- **一路自信、一路无感时会惩罚正确结果**：查 `400` 时 BM25 给含正确答案的块第 3 名，向量给第 8 名（纯数字在语义空间几乎无信号），RRF 双份分相加后反而输给"两路都排得还行"的噪声块。
- **治不了两路同时误命中**：查 `怎么防止模型乱编` 时两路都误判同一个无关块，融合后它照样第一。
- **万能块**：示例数据里的"检索验证清单"汇总了所有测试题答案，对任何 query 都排第一。它给的是二手摘要，会挤掉原始论述。真实语料里对应目录页、FAQ 汇总页。

**应对**：RRF 分差仅 5% 时排序本身已不可靠，与其优化排序，不如把 `k` 从 3 调到 5 放大召回范围，让 LLM 自己从更多资料里判断——实测 `k=5` 后歧义问题 `400 是什么意思` 从"只答 HTTP 400"变成"同时答出 HTTP 400 与 chunk_size=400 两层含义"。

**Query 改写：检索用的 query 和人读的 query 不是一回事**

口语化问题会让 BM25 完全失效——`切片切多大合适` 的 token（`切片 / 切多 / 多大 / 大合 / 合适`）在资料里一个都不存在，BM25 直接返回空列表。向量那边则被"询问数量"的语义带偏，把讲运动的块（"每周三次、每次三十分钟"）排到第一：**它匹配的是「语义类型」，不是「主题」。**

改写规则有三条，都是实测撞出来的：

1. **必须注入语料术语提示**。否则 LLM 在盲改——问"切片切多大"，它按通用编程知识改成了"数组切片 / 数据分片"，而资料里写的是 `chunk_size` / `切块长度`。
2. **输出关键词组合，不要输出完整问句**。"多少 / 怎么 / 咋"这些疑问词本身就是噪声源，会把含数字的块捞上来。
3. **原问题要保留参与融合**。改写会丢信息——`这玩意儿咋配` 里的"配"字能被 BM25 命中"配置"，改写成 `chunk_size chunk_overlap` 后这个信号就没了（实测去掉原问题后，该 query 的正确答案从第 1 掉到第 3）。

实测效果：

| query | 单路融合 Top3 | 多路 Top3 |
|---|---|---|
| `切片切多大合适` | **8**, 9, 3 | 9, **3**, 8 |
| `这玩意儿咋配` | **3**, 2, 7 | **3**, **4**, 9 |
| `top_k 取多少` | 9, **4**, 6 | 9, **4**, 6 |

第二行里 `chunk_4` 从"不在 Top5"升到第 2 —— **不同角度的改写覆盖了不同的正确答案**，这是多路检索的核心收益。

多路检索是**两层 RRF 嵌套**：内层 `hybrid_retrieve` 融合向量与 BM25，外层 `multi_retrieve` 融合多个 query 的结果。因为 RRF 只依赖名次、不依赖分数，同一个公式既能融检索器也能融 query。

**局限**：Query 改写只提升召回，不消除噪声。向量给无关块的基础相似度（0.35~0.4）和"答案汇总块"通吃的问题依旧存在——实测把原问题去掉后，无关块只是从第 3 降到第 4，仍在 Top5。这两类只能靠 rerank 解决。

**多轮对话：历史必须先影响检索**

普通聊天机器人把历史拼进 prompt 就够了，RAG 不行。用户问"它跟 overlap 什么关系"，如果直接拿这句话去检索：

- **BM25**：`它`、`跟` 都是废词，只有 `overlap` 能命中，方向已经跑偏
- **向量**：语义太模糊，排序基本随机

**只把历史拼进生成 prompt 是不够的——检索阶段就错了，LLM 再聪明也救不回来。**

所以多轮 RAG 的正确做法是：**先用「历史 + 当前问题」把问题改写成独立完整的句子，再检索。**

实测（同一句话，历史不同则消解结果不同）：

| 历史上一轮 | 原问题 | 改写后（standalone） |
|---|---|---|
| `chunk_size 是多少？` | `它跟 overlap 什么关系？` | `chunk_size 跟 overlap 是什么关系？` |
| `top_k` | `它跟 overlap 什么关系？` | `top_k 跟 overlap 有什么关系？` |

**同一个"它"，因为历史不同消解成了不同的名词**——说明它真的在读历史，不是瞎猜。

**Prompt 约束的两个坑**（都是实测撞出来的）：

1. **抽象约束对推理模型无效**。"不要添加原问题没有问的内容"这条写上去，LLM 会自己解释成"应该帮用户想周全"，把 `那 top_k 呢？` 扩写成 `top_k 是什么，以及它和 chunk_size、chunk_overlap 有什么关系`。
   → 换成**具体反例 + 可量化限制**才管用：`"那 top_k 呢？"只能写成"top_k 是多少？"，绝不能写成"...有什么关系？"` 加上 `改写结果不超过原问题的 2 倍长度`。
2. **首轮必须跳过改写**：`if not history: return question` —— 没有历史就没有指代可消解，白花 2~4 秒。

**流式的特殊处理**：`ask_stream_chat` 是生成器，生成过程中拿不到完整答案。做法是在循环里累积 `full`，`for` 循环结束后再写两条 `messages`。**`full` 只累积 `delta.content`，不累积 `reasoning_content`** —— 思考过程存进历史会污染下一轮上下文。代价是客户端中途断开会丢历史（`GeneratorExit` 中断，写库不执行），这可以接受。

**已知问题**：当前 `/chat/stream` 把 `reasoning_content`（思考）和 `content`（正文）混在同一个纯文本流里，用户会看到思考过程。这是阶段三为了把 TTFT 从 17s 降到 1s 做的取舍。正确解法是 **SSE 分类型**（每块带 `{"type": "reasoning" | "content"}` 标签，前端把思考放折叠区），计划在阶段六实现。

**防幻觉策略**

- Prompt 显式约束"只使用资料中的信息，不要编造"
- 资料不足时要求回答"资料中没有提到"
- 资料涉及多个含义时要求分别说明（实测：不加这条时，歧义问题只答其中一个含义）
- 检索结果按分数排序后取 Top-K，附带来源块 ID 便于排查

**流式输出：推理模型的 `reasoning_content` 不能丢**

`deepseek-flash` 是推理模型，流式 delta 里有两个字段：`reasoning_content`（思考过程）和 `content`（正式回答）。实测发现，**思考阶段 `content` 恒为 `None`** —— 若只转发 `content`，首字延迟就等于整个思考时长（实测 17s 以上，期间屏幕一片空白，看起来像卡死）。

把思考过程一并 `yield` 出去之后，首字延迟降到约 1s，且思考内容本身会滚动十几秒，流式效果一眼可见。

> **TTFT（首字延迟）才是流式体验的核心指标，不是总耗时。** 用户感知的是"多久开始出字"，而不是"多久全部出完"。

引入多轮对话后，TTFT 会从约 1 秒涨到约 4 秒——检索前多了"消解指代"这一步（推理模型改写 2~3 秒）。这是"更准"换"更慢"的取舍。

优化方向的实测依据：把语料从 39 块降到 10 块（检索量减少 74%）后，总耗时几乎不变——**说明瓶颈在 LLM 调用，不在检索**。所以该优化的是「3 次 embedding 并发」或「改写换非推理模型」，而不是检索算法或向量库。
